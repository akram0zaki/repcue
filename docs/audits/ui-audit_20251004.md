### 1) Timer display shadows use inline styles
- **Component**: `apps/frontend/src/pages/TimerPage.tsx`
- **Issue**: Multiple inline `style={{ textShadow: '...' }}` on countdown/rep/time labels.
- **Why noncompliant**: UI spec requires styling via global tokens/utilities; inline styles violate centralized theming and maintainability.
- **Actual**:
```798:826:apps/frontend/src/pages/TimerPage.tsx
<div className="text-4xl font-bold text-white" style={{ textShadow: '2px 2px 4px rgba(0,0,0,0.8), -1px -1px 2px rgba(0,0,0,0.8), 1px -1px 2px rgba(0,0,0,0.8), -1px 1px 2px rgba(0,0,0,0.8)' }}>
  {countdownTime}
</div>
<div className="text-sm text-white mt-1" style={{ textShadow: '1px 1px 2px rgba(0,0,0,0.8)' }}>
  {t('timer.getReadyEllipsis')}
</div>
```
- **Correct**: Define `.timer-text-shadow-lg` and `.timer-text-shadow-sm` in `src/styles/tokens.css` (light/dark aware if needed), then apply class names: `className="text-h2 timer-text-shadow-lg"` and `className="text-caption timer-text-shadow-sm"`.
- **Notes**: Verify reduced-motion variants if any animation is tied to text presentation.

### 2) Inline sizing and transforms in TimerPage
- **Component**: `apps/frontend/src/pages/TimerPage.tsx`
- **Issue**: Inline `style={{ width: '280px', height: '280px' }}`, WebKit transforms for video.
- **Why noncompliant**: Sizing and GPU-hints must live in global utilities to enable design changes centrally.
- **Actual**:
```459:480:apps/frontend/src/pages/TimerPage.tsx
<div className={`relative mx-auto mb-3 ${repPulse ? 'transition-transform' : ''}`} style={{ width: '280px', height: '280px' }} />
...
style={{ WebkitTransform: 'translateZ(0)', transform: 'translateZ(0)', WebkitBackfaceVisibility: 'hidden', backfaceVisibility: 'hidden' }}
```
- **Correct**: Introduce utilities e.g. `.timer-square-280`, `.gpu-accelerated` in global stylesheet; replace inline styles with those utilities. Prefer responsive width classes per UI spec.
- **Notes**: Ensure 320px viewport compliance; consider making the size responsive (`w-full max-w-[280px] aspect-square`).

### 3) Progress bars using inline width styles
- **Components**:
  - `apps/frontend/src/pages/TimerPage.tsx` (workout progress)
  - `apps/frontend/src/components/ForceUpdateModal.tsx` (force/update progress)
  - `apps/frontend/src/components/WorkoutForceUpdateModal.tsx`
  - `apps/frontend/src/components/OnboardingFlow.tsx`
- **Issue**: `style={{ width: [...%] }}` applied inline to progress bars.
- **Why noncompliant**: Inline styles break theming and maintenance.
- **Actual**:
```336:385:apps/frontend/src/components/ForceUpdateModal.tsx
<div className="bg-white h-1 rounded-full transition-all duration-1000" style={{ width: `${((300 - timeUntilForce) / 300) * 100}%` }} />
...
<div className="bg-blue-600 h-2 rounded-full transition-all duration-300" style={{ width: `${updateProgress}%` }} role="progressbar" />
```
- **Correct**: Create a `ProgressBar` component that accepts a `value` prop and applies width via CSS custom property `--progress` on a child element. Example: `.progress__bar { width: calc(var(--progress) * 1%); }` set via class binding or inline `style={{ '--progress': value }}` typed as CSSProperties. Centralize colors via tokens.
- **Notes**: Reuse across all progress indicators.

### 4) Inline direction styles for RTL-protected controls
- **Components**:

  - `apps/frontend/src/components/CatalogSelector.tsx`
- **Issue**: `style={{ direction: 'ltr' }}` on buttons.
- **Why noncompliant**: UI spec mandates CSS protection classes rather than inline styles; see `ui-specs.md` section “RTL Icon Rendering”.
- **Actual**:
```110:123:apps/frontend/src/components/Navigation.tsx
<button ... data-testid="nav-more" style={{ direction: 'ltr' }}>
  <MoreIcon size={26} />
</button>
```
- **Correct**: Use `.nav-more-button { direction: ltr !important; }` and scoped CSS in global stylesheet. Apply `className="nav-more-button"` without inline `style`.
- **Notes**: Ensure `.nav-dropdown` and icon SVGs are covered by global RTL rules per spec.

### 9) Ad‑hoc Tailwind color utilities bypass semantic tokens
- **Components**: Many (e.g., Settings/Loading/LazyRoutes)
- **Issue**: Classes like `bg-blue-600`, `text-gray-600`, `dark:bg-gray-900` appear widely instead of semantic tokens/classes (`bg-surface-*`, `text-text-*`, `.btn-*`).
- **Why noncompliant**: UI spec and tokens require consistent semantic palette; ad‑hoc utilities hamper global theming.
- **Actual**:
```24:32:apps/frontend/src/router/LazyRoutes.tsx
<div className="animate-spin ... border-b-2 border-blue-600"></div>
<p className="text-gray-600 dark:text-gray-400">Loading...</p>
```
- **Correct**: Replace with tokenized classes (e.g., `border-primary-500`, `text-text-600`) and standardized loader component.
- **Notes**: Audit across: `SettingsPage`, `App` loading fallback, buttons using raw `bg-red-600`, `bg-green-600`, etc. Migrate to `.btn-primary`, `.btn-danger`, etc.

### 10) Hardcoded `aria-label` and visible text without i18n

- **Issue**: Direct string literals in ARIA/labels bypass i18n.
- **Why noncompliant**: `docs/i18n-guide.md` mandates all user-facing strings through i18n.
- **Actual**:
```115:121:apps/frontend/src/components/Navigation.tsx

```
- **Correct**: Use `t('a11y.moreOptions')`, `t('a11y.clearSearch')`, `t('a11y.scrollLeft')`, etc. Ensure keys exist in `public/locales/*/a11y.json`.
- **Notes**: Tests may hardcode labels; prefer data-testid when asserting or import i18n.
