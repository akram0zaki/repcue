# Coach Page UI/UX Conformance Audit Report
**Date**: October 17, 2025

**Component**: Coach Page (`apps/frontend/src/pages/CoachPage.tsx`)  
**Reference Guides**: 
- `docs/style-guide.md`

## Executive Summary

The Coach Page is **64% compliant** with RepCue's style guide and UI specifications. While the component demonstrates good structure and accessibility foundations, it has **14 moderate-to-high compliance gaps** spanning typography, styling, RTL support, mobile-first design, and semantic markup. Most issues are straightforward to fix with focused refactoring.

**Key Findings**:
- ✅ Strong accessibility (ARIA labels, semantic markup, focus management)
- ✅ Proper i18n integration with translation keys
- ✅ Good loading/error/empty state handling
- ❌ Extensive use of ad-hoc Tailwind color classes instead of semantic tokens
- ❌ Inconsistent typography scale (mixing `.text-*` with inline sizes)
- ❌ RTL layout issues in activity logs and card elements
- ❌ Hardcoded pixel values and excessive fixed widths
- ❌ Missing semantic text color tokens in multiple areas
- ❌ Improper use of utility classes vs. semantic composition

#### Finding 1: Inconsistent Heading Styles
**Severity**: HIGH  
**Location**: CoachPage.tsx lines 215-217, 246-248, 375-376, etc.

The component uses hardcoded Tailwind typography classes instead of semantic tokens:

```tsx
// CURRENT (NON-COMPLIANT)
<h1 className="text-2xl font-bold text-text-900 dark:text-text-50">
  {t('coaching:title')}
</h1>

// SPEC REQUIREMENT
<h1 className="text-h1">
  {t('coaching:title')}
</h1>
```

**Issues**:
- `text-2xl` doesn't match any semantic scale (should be `.text-h1` = 32px)
- `font-bold` is ad-hoc when `.text-h1` includes proper weight
- Duplicates color classes when `.text-h1` handles dark mode automatically

**Instances Found**: 12+ throughout CoachPage.tsx

### 1.2 Color & Styling Compliance

**Status**: ⚠️ **CRITICAL** (25% compliant)

#### Finding 6: Extensive Ad-Hoc Tailwind Color Classes
**Severity**: CRITICAL  
**Location**: CoachPage.tsx lines 228-237, 251-260, 314-340, etc.

The component extensively uses ad-hoc Tailwind color utilities instead of semantic tokens:

```tsx
// CURRENT (NON-COMPLIANT) - Examples:
<div className="bg-red-50 dark:bg-red-900/20 border border-red-200 dark:border-red-800">
<div className="bg-warning-soft border border-warning rounded-lg p-4">
<div className="bg-blue-50 dark:bg-blue-900/20 rounded-xl p-4 shadow-sm border border-blue-200 dark:border-blue-800">
<div className="bg-white dark:bg-gray-800 rounded-xl p-4 shadow-sm border border-gray-200 dark:border-gray-700">
<div className="bg-purple-50/50 dark:bg-purple-900/10">
<div className="px-2 py-1 rounded-full text-small font-medium bg-blue-100 dark:bg-blue-200 text-blue-800 dark:text-blue-900 whitespace-nowrap shrink-0">

// COMPLIANT (SEMANTIC TOKENS)
// Error state: bg-error-soft, border-error, text-error
// Warning state: bg-warning-soft, border-warning, text-warning
// Success state: bg-success-soft, border-success, text-success
// Neutral: bg-surface-0, border-surface-200, text-text-primary
```

**Issues**:
- Creates maintenance burden (12+ color combinations across 2 themes)
- Violates design system (tokens.css not used)
- Makes theme changes impossible without exhaustive refactoring
- Low contrast combinations in dark mode (e.g., `dark:bg-blue-900/20` with `text-blue-800`)

**Instances Found**: 20+

### 1.3 Mobile-First & Responsive Design

**Status**: ⚠️ **PARTIAL** (60% compliant)

#### Finding 11: Fixed Width Constraints Not Mobile-First
**Severity**: MEDIUM  
**Location**: CoachPage.tsx lines 208, 213-214, 237, etc.

```tsx
// CURRENT
<div className="max-w-4xl mx-auto">
  {/* Content */}
</div>

// ISSUE: max-w-4xl on mobile = 56rem = 896px
// On 320px device, causes unnecessary overflow management
// Should be mobile-first:

// COMPLIANT
<div className="w-full sm:max-w-4xl mx-auto px-4 sm:px-0">
  {/* Content naturally fits on mobile, constrained on desktop */}
</div>
```

**Issues**:
- `max-w-4xl` doesn't prevent overflow issues on devices < 420px
- Mobile-first approach requires responsive width constraints
- Missing `px-4` padding on mobile container

**Impact**: On 320px screens (iPhone SE), edges may feel cramped

---

#### Finding 12: Card Padding Not Responsive
**Severity**: MEDIUM  
**Location**: CoachPage.tsx lines 195, 232, 251, 288, 314, etc.

```tsx
// CURRENT (SAME PADDING EVERYWHERE)
<div className="bg-white dark:bg-gray-800 rounded-xl p-4 shadow-sm border">

// COMPLIANT (RESPONSIVE PADDING)
<div className="bg-white dark:bg-gray-800 rounded-xl p-3 sm:p-4 shadow-sm border">
// Or for larger cards:
<div className="bg-white dark:bg-gray-800 rounded-xl p-4 sm:p-5 lg:p-6 shadow-sm border">
```

**Issues**:
- `p-4` (1rem) may be excessive on mobile (UI spec: "compact component variants by default")
- No responsive padding adjustments for tablet/desktop
- Violates "Space is Sacred" principle on mobile

**Instances Found**: 10+

#### Finding 13: Horizontal Overflow Risk in Activity Log
**Severity**: HIGH  
**Location**: CoachPage.tsx lines 322-324, 389-392

```tsx
// PROBLEMATIC LAYOUT
<div className="flex flex-wrap items-center gap-2 sm:gap-4">
  <div className="flex items-center gap-1 shrink-0">
    <svg className="w-4 h-4" />
    <span className="whitespace-nowrap">{formatTime(...)}</span>
  </div>
  <div className="flex items-center gap-1 shrink-0">
    <svg className="w-4 h-4" />
    <span className="whitespace-nowrap">{formatDuration(...)}</span>
  </div>
  <div className="flex items-center gap-1 shrink-0">
    <svg className="w-4 h-4" />
    <span className="whitespace-nowrap">{t('common:activity.exerciseCount', { count: 3 })}</span>
  </div>
</div>

// ISSUE on 320px:
// - Each metadata item: ~40px (icon) + text
// - 3 items × ~80px = 240px+ 
// - With gap-2: +16px = 256px BEFORE card padding
// - Card padding: 2×16px = 32px
// - TOTAL: 288px > 320px = OVERFLOW!

// COMPLIANT (RESPONSIVE STACK)
<div className="flex flex-col gap-1 sm:flex-row sm:flex-wrap sm:gap-3 text-sm">
  <div className="flex items-center gap-1 shrink-0">
    <svg className="w-4 h-4" />
    <span>{formatTime(...)}</span>
  </div>
  {/* ... */}
</div>
```

**Issues**:
- Metadata row likely overflows on 320px screens
- `whitespace-nowrap` prevents wrapping but forces overflow
- Gap size (sm:gap-4) too large for mobile

**Impact**: Horizontal scrolling on iPhone SE (320px) - WCAG violation

### 1.4 RTL (Right-to-Left) Support

**Status**: ❌ **CRITICAL** (0% compliant for RTL protections)

#### Finding 15: Missing RTL Icon Protections in Navigation
**Severity**: CRITICAL  
**Location**: CoachPage.tsx lines 235, 412-416, 432-436

```tsx
// CURRENT (NO RTL PROTECTION)
<button
  onClick={handleRefresh}
  className="p-2 text-gray-600 hover:text-gray-900 rounded-lg"
>
  <svg className="w-5 h-5" fill="none" stroke="currentColor" viewBox="0 0 24 24">
    <path d="M4 4v5h.582m15.356 2A8.001 8.001 0 004.582 9m0 0H9m11 11v-5h-.581m0 0a8.003 8.003 0 01-15.357-2m15.357 2H15" />
  </svg>
</button>

// ISSUE in RTL mode:
// - SVG refresh icon may mirror/distort
// - No direction: ltr force (per RTL guide)
// - Navigation icons get affected by global RTL rules

// COMPLIANT (PER RTL GUIDE)
<button
  onClick={handleRefresh}
  className="nav-more-button"
  style={{ direction: 'ltr' }}
>
  <svg className="w-5 h-5" fill="none" stroke="currentColor" viewBox="0 0 24 24">
    <path d="..." />
  </svg>
</button>

// Or better: use centralized NavigationIcons component
<RefreshIcon className="w-5 h-5" />
```

**Issues**:
- Refresh icon not protected for RTL (will distort in Arabic)
- Expand/collapse arrows in activity logs need RTL protection
- SVG icons may mirror unexpectedly in RTL

**Instances Found**: 3 (refresh button, two expand/collapse arrow sets)
